## 1. 部署前检查

必备条件：

- Python 3.11，或可运行项目镜像的 Docker 环境。
- 可访问的 OpenAI 兼容模型服务。
- 有效的 `MODEL_SERVICE_URL` 和 `API_KEY`。
- `uploads/`、`results/`、`logs/`、`schemas/` 的可写空间。
- 生产环境的入口鉴权、网络隔离、限流和 PII 管理方案。

当前任务状态仅存在单进程内存中，所以生产部署应保持单副本。启用多副本前必须先迁移任务存储和幂等键。

## 2. 配置

创建本地配置：

```bash
cp .env.example .env
```

最低配置：

```env
MODEL_SERVICE_URL=http://<llm-host>:<port>/v1
API_KEY=<model-api-key>
```

### 2.1 运行时配置表

| 变量 | 代码默认值 | 说明 |
|---|---|---|
| `MODEL_SERVICE_URL` | 无，缺失则启动失败 | OpenAI 兼容服务地址 |
| `API_KEY` | 无，缺失则启动失败 | 模型服务密钥 |
| `MODEL_NAME` | `Qwen3.5-397B-A17B` | 默认模型 |
| `ASYNC_MODEL_NAME` | 同 `MODEL_NAME` | 异步路由模型 |
| `SYNC_MODEL_NAME` | 同 `MODEL_NAME` | 同步路由模型 |
| `FALLBACK_MODELS` | 空 | 逗号分隔备用模型 |
| `TEMPERATURE` | `0.01` | 推理温度 |
| `MAX_TOKENS` | `16384` | 最大输出 token |
| `MAX_WORKERS` | `24` | 全局线程池和解析信号量上限 |
| `API_TIMEOUT` | `300` | 单次模型请求超时秒数 |
| `MAX_RETRIES` | `2` | OpenAI 客户端重试次数 |
| `LLM_PREFIX_CACHE_ENABLED` | `true` | 为简历解析请求发送稳定 `prompt_cache_key`；模型服务端需启用或原生支持前缀缓存 |
| `DOWNLOAD_TIMEOUT` | `60` | URL 下载超时秒数 |
| `MAX_FILE_SIZE_MB` | `20` | 输入大小限制 |
| `SYNC_DOCUMENT_MAX_TEXT_CHARS` | `120000` | 同步文本字符预算 |
| `TASK_TTL_MINUTES` | `120` | 内存任务保留时长 |
| `SERVICE_PORT` | `21804` | 服务端口 |
| `UPLOAD_DIR` | `<project>/uploads` | 上传/下载目录 |
| `RESULT_DIR` | `<project>/results` | 结果目录 |
| `TAGS_ADMIN_TOKEN` | 空 | 标签写接口管理 Token |

`.env.example` 是推荐部署值，不一定等于代码回退值。例如模板当前将 `MODEL_NAME` 设置为 `Qwen3.6-35B-A3B`、`MAX_TOKENS` 设置为 `4096`。实际运行以注入环境变量为准。

### 2.2 Langfuse

同时配置 `LANGFUSE_SECRET_KEY` 和 `LANGFUSE_PUBLIC_KEY` 后启用追踪。可选配置包括：

```env
LANGFUSE_BASE_URL=http://<langfuse-host>:3000
LANGFUSE_TRACING_ENVIRONMENT=production
LANGFUSE_TAGS=resume-parser,v3.1
```

未配置时应静默降级，不影响主流程。

`.env.example` 中的 Langfuse Key 是占位符。若不使用 Langfuse，应将两个 Key 和 URL 显式置空，避免以无效占位值误启用追踪。

## 3. 本地启动

```bash
python -m pip install -r requirements.txt
uvicorn app:app --host 0.0.0.0 --port 21804
```

验证：

```bash
curl -fsS http://localhost:21804/health
curl -fsS http://localhost:21804/v1/models
curl -fsS http://localhost:21804/openapi.json -o /tmp/ai-resume-openapi.json
```

`/health` 只验证进程存活。必须再使用测试文档执行一次真实模型解析，才能确认模型、网络和文件存储就绪。

## 4. Docker Compose

```bash
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker logs --tail 200 ai-resume-parsertag
```

默认挂载：

| 宿主机 | 容器 |
|---|---|
| `./logs` | `/app/logs` |
| `./uploads` | `/app/uploads` |
| `./results` | `/app/results` |
| `./schemas` | `/app/schemas` |

注意：挂载整个 `schemas/` 会覆盖镜像内同名目录。部署前要确保宿主机包含完整 Schema、静态标签和运行时配置文件，而不是只有空目录。

停止服务：

```bash
docker compose down
```

## 5. 离线部署

`localmaterial/offline` 当前已有镜像标记为 `v3.1.1-20260805`，早于
`ai-resume-parsertag:ID-mapping-tag:V1.0.1-20260806` 映射、公共 ID 输出和时间线重叠修复，**不是当前代码的
最新离线包**。部署当前版本前必须在当前工作区重新执行打包脚本，并以新生成包覆盖
交付介质；不能只替换 `data/schemas` 来宣称代码已升级。

离线包位于 `deploy/offline/`，详细命令见 `deploy/offline/README.md`。基本流程：

```bash
cd deploy/offline
./offline.sh deploy
./offline.sh status
./offline.sh logs
```

离线包使用 `linux/amd64` 镜像；ARM Mac 依赖 Docker Desktop 模拟，内网 Linux AMD64 可原生运行。

重新打包不会删除离线目录中的 `.env`、`data/logs`、`data/uploads`、`data/results`
和已有 `data/schemas/tag_config_runtime.json`。镜像、部署模板及其他 Schema 会更新；
部署前仍应对离线目录做独立备份。

## 6. Kubernetes 与 GitLab CI

当前 `.gitlab-ci.yml` 会在 `dev`/`main` 构建本地镜像并部署到 `demo` 命名空间，使用单副本和 NodePort `30804`。

当前清单不能视为完整生产部署，存在以下阻断项：

1. 应用要求 `API_KEY`，但 Deployment 只注入 `MODEL_SERVICE_URL` 和 `SERVICE_PORT`，Pod 会在导入配置时启动失败。
2. 没有 Kubernetes Secret、PVC、readinessProbe、securityContext 和非 root 用户。
3. 内存 limit 为 512 MiB，与多页视觉解析和默认 24 线程存在 OOM 风险。
4. CI 没有运行 pytest、lint、依赖扫描或镜像扫描。
5. `imagePullPolicy: Never` 要求目标节点本地已有同名镜像。

上线前至少需要通过 Secret 注入 `API_KEY`/管理 Token，增加 PVC、readiness、资源压测和 CI 测试阶段。不要仅凭现有 Pipeline 成功状态判断服务可用。

## 7. 日志和数据目录

日志按 `logger/log_config.yml` 配置输出，文件名按日期、进程和级别组织。排障常用：

```bash
docker logs --tail 200 ai-resume-parsertag
rg 'ERROR|任务失败|模型.*失败' logs
rg '<taskId或前8位>' logs
```

敏感性：

- `results/` 保存完整结构化简历。
- 除 `/health`、`/openapi.json` 外，JSON 接口会先记录完成信息 JSON，再逐行记录
  与实际响应一致的完整 JSON；异步轮询中间态降为 DEBUG，终态为 INFO。
- HTTP 4xx 或非零业务码使用 WARNING，HTTP 5xx 使用 ERROR。控制台日期为蓝色，
  DEBUG/INFO/WARNING/ERROR 分别为青/绿/黄/红色；文件日志不带 ANSI 颜色。
- `uploads/` 可能保留异常中断产生的原始文件。
- `schemas/tag_config_runtime.json` 是线上标签配置状态。

运维必须配置目录权限、磁盘监控、加密备份和清理周期。清理前先确认业务保留要求，并只对明确的 `uploads`、`results`、`logs` 子目录操作。

## 8. 监控建议

| 类别 | 指标/告警 |
|---|---|
| 可用性 | 进程存活、真实模型探测成功率 |
| 延迟 | 解析、打标和全链路 P50/P95/P99 |
| 模型 | 主模型错误率、回退次数、超时、token/字符量 |
| 任务 | 0/1/2/3/4 状态数量、最长运行时长、TTL 删除量 |
| 资源 | RSS、线程数、CPU、打开文件数、磁盘使用率 |
| 数据 | 上传残留数、结果文件增长、日志增长 |

当前 `/health` 不适合作为 readiness。可在部署层增加真实依赖探针，但应控制探测频率，避免产生高额模型调用。

## 9. 故障处理

### 9.1 服务启动失败

1. 检查 `MODEL_SERVICE_URL` 和 `API_KEY` 是否注入。
2. 检查 `schemas/` 挂载是否包含完整文件。
3. 查看容器首屏 traceback。
4. 验证端口没有被占用，目录可写。

### 9.2 模型超时或回退

1. 从日志确认实际模型和失败类型。
2. 直接检查模型服务网络和 `/v1/models`（若后端提供）。
3. 检查 `API_TIMEOUT`、`MAX_RETRIES` 和 `FALLBACK_MODELS`。
4. 降低业务并发，避免大量重试进一步压垮模型服务。

### 9.3 任务查询不到

可能原因：

- 任务已超过 `TASK_TTL_MINUTES`。
- 服务重启导致内存任务丢失。
- 请求被负载均衡到另一个副本。
- 长任务从创建时间起超过 TTL，运行中记录被清理。

`results/` 可能仍有结果文件，但当前没有通过 taskId 重建任务状态的 API。

### 9.4 内存过高/OOM

1. 降低 `MAX_WORKERS` 和同步请求 `max_concurrency`。
2. 限制扫描 PDF 页数和同时提交量。
3. 提高容器内存前先压测峰值 RSS。
4. 检查多页面 PDF/DOCX 的局部线程池和页面图像是否同时驻留。

### 9.5 标签配置损坏

结构守卫通常会拒绝不合法更新。若文件因外部编辑损坏：

1. 备份 `schemas/tag_config_runtime.json`。
2. 对照 `tag/tag_config.py` 和 Schema 检查结构。
3. 在确认允许恢复默认值后调用 `/api/tags/config/reset`。

## 10. 发布与回滚

发布前：

```bash
pytest -q
docker build -t ai-resume-parsertag:<version> .
```

并分别完成异步视觉 PDF/DOCX/JPEG/PNG、同步文本 PDF、扫描 PDF、标签配置和模型回退验收。异步模型输入必须始终为图片。

回滚应使用上一已验证镜像，并同时恢复与该版本匹配的 `schemas/`。运行时标签配置可能与旧代码结构不兼容，回滚前必须备份和校验。由于任务状态不持久化，容器重启会使在途任务丢失，应先停止新流量并等待或记录在途任务。

## 11. 安全基线

生产上线前必须落实：

- API 鉴权、租户隔离和 `/api/tasks` 权限控制。
- URL 协议/IP/域名白名单与 DNS 重绑定防护。
- `type=file` 固定根目录或生产禁用。
- CORS 来源白名单、请求限流和有界任务队列。
- PII 日志脱敏、结果加密、保留期限和删除审计。
- 容器非 root、只读根文件系统、最小权限 Secret 和依赖扫描。
