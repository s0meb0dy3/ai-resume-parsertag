# AIHR 简历解析服务 — 优化方向分析

> 版本：v1.2  日期：2026-05-28

---

## 优化目标总览

| 目标 | 当前痛点 | 核心优化手段 | 预期效果 |
|:----:|---------|------------|---------|
| **快** | 全流程 45~90s，多模态 LLM 调用占主要耗时 | MinerU 本地 PDF 解析；打标输入压缩；MD5 缓存；并发打标 | 标准简历全流程缩短至 **10~20s** |
| **准** | 结构化字段格式漂移；跨批次合并精确匹配易拆分；打标规则覆盖不足 | 规则后校验层；模糊合并策略；静态词典补强；MinerU 降低排版噪声 | 关键字段准确率提升，跨批漏字段减少 |
| **稳** | LLM 超时/失败无分级降级；扫描件/加密 PDF 无前置拦截 | MinerU → 小多模态模型 → 397B 三级降级；PDF 预检增强；LLM 独立超时 | 异常场景有保底，避免全链路失败 |
| **省** | 每份简历至少 1 次多模态大模型调用；打标 Prompt 含大量无效长文本 | MinerU 替代多模态 OCR；打标去掉 description；规则层前置；小模型替代 | 多模态 token 减少 **80%+**，打标 token 减少 **40~60%** |
| **管** | 标签规则仅支持 API 调用修改，无可视化界面；配置变更无审计记录；院校/大厂静态名单修改需重启服务 | 管理后台 UI（标签维度增删改查）；配置变更日志；静态数据热加载（无需重启） | 运营人员可自助调整打标规则，降低维护成本 |

> 服务定位：纯无状态中台，不持久化业务数据，存储由调用方负责。内存任务缓存（TTL 10min）和本地配置文件（`tag_config_runtime.json`）均为设计取舍，不纳入优化范围。

---

## 定位说明

本服务为**纯无状态中台服务**：不持久化业务数据，不负责简历/标签存储，调用方自行入库；
内存任务缓存（TTL 10min）和本地 `tag_config_runtime.json` 均为轻量中台的设计取舍，不作为扩展性优化目标。

## 1. 降低多模态大模型依赖（核心优化目标）

**现状**：
- 阶段一（OCR 解析）：每份简历至少 1 次多模态 LLM 调用，调用 Qwen3.5-397B-A17B；超过 8 页时分批，每批独立发起多模态调用，token 消耗随页数线性增长。
- 阶段二（打标）：1 次**纯文本** LLM 调用，但 Prompt 注入了完整简历 JSON（含 `works[].description`、`projects[].description` 大段文本）。
- 已有规则降级层（`extract_positive_tags_rule`），LLM 失败时自动回退，但日常路径未充分利用。

### 1.1 引入 MinerU 替代多模态 OCR

[MinerU](https://github.com/opendatalab/MinerU) 是上海 AI Lab 开源的高质量 PDF 解析工具，内部集成 DocLayout-YOLO 版面检测 + PP-StructureV2 表格识别，输出结构化 Markdown，无需多模态 LLM 即可完成 PDF 文字/表格/段落提取。

**接入方案**：

```
PDF 输入
   │
   ▼
MinerU 解析（本地部署，CPU/GPU 均可）
   ├─ 成功 → 输出结构化 Markdown
   │         ↓
   │    纯文本 LLM（小模型）提取结构化字段  ← 完全跳过多模态调用
   │
   └─ 失败（加密/扫描件质量差）→ 降级回原多模态路径
```

**预期收益**：
- 标准排版简历（占比 80%+）可完全跳过多模态 LLM，OCR 阶段 token 消耗降至 0
- MinerU 本地运行，延迟约 2~5s，远低于当前 20~40s 的多模态调用
- 对扫描件/复杂表格简历保留多模态降级路径，不损失覆盖率

### 1.2 引入开源小多模态模型

对 MinerU 无法处理的场景（手写/扫描件/特殊排版），可用轻量开源多模态模型替代 397B 大模型：

| 模型 | 参数量 | 适用场景 | 备注 |
|------|--------|---------|------|
| **InternVL2-8B** | 8B | 文档图像理解、表格提取 | 上海 AI Lab，文档类任务 SOTA |
| **Qwen2-VL-7B** | 7B | 通用 OCR、多语言文档 | 阿里，中文简历效果好 |
| **GOT-OCR 2.0** | 580M | 纯 OCR 任务，输出 Markdown | 专用 OCR 模型，速度极快 |
| **MiniCPM-V 2.6** | 8B | 端侧部署，低显存 | 推理可在单张 A10 上运行 |

**推荐路径**：内网部署 InternVL2-8B 或 Qwen2-VL-7B（vLLM 服务），作为 MinerU 失败时的二级降级，397B 模型仅作为最终兜底。

### 1.3 压缩打标输入

打标阶段（纯文本调用）当前注入完整简历 JSON，`description` 长文本对 5 维度打标无实质贡献：

- 只传 `works[].company/position/startDate/endDate`、`educations[].school/degree`、技能关键词
- 去掉所有 `description` 字段
- 预计 token 降低 **40~60%**，打标耗时由 5~20s 缩短至 3~10s

### 1.4 规则层前置 + 缓存

| 方案 | 说明 |
|------|------|
| 规则层前置 | 学历（院校名单匹配）、工作年限（日期计算）、公司背景（大厂关键词）优先走规则层，仅 skills/industry 走 LLM；对确定性维度减少 LLM 调用 |
| MD5 结果缓存 | 对相同 PDF 内容（MD5 一致）直接返回缓存结果，批量重投场景可减少 50%+ LLM 调用 |

## 2. 解析与打标准确性

**现状**：
- 电话、邮件、日期等强结构化字段依赖 LLM 提取，容易格式漂移，`json_repair` 兜底率较高。
- 超过 8 页时分批并发，跨批次合并用 `company+startDate` 精确匹配，公司名称轻微差异（缩写/全称）会导致同一段工作经历重复或拆分。
- LLM 修复字段无可信度标记，调用方无法感知低置信风险字段。

**优化方向**

- **规则后校验层**：LLM 输出后用正则修正关键字段——电话 `1[3-9]\d{9}`、邮件标准格式、`startDate/endDate` 统一 `YYYY-MM`，减少 `json_repair` 介入频率。
- **模糊合并策略**：跨批次合并 `works[]` 时改用公司名编辑距离匹配（容忍缩写/全称差异），避免同一段经历被拆分。
- **置信度标注**：对 `json_repair` 修复的字段打 `_repaired` 内部标记，供调用方识别低可信字段。
- **MinerU 引入后**：文字型简历可先经 Markdown 规范化，再用 LLM 提取结构，减少排版噪声对字段提取的干扰。
- **静态数据补强**：定期扩充 `tag_data.py` 中的院校/大厂/行业词典，提升规则层覆盖率，降低对 LLM 的依赖。

## 3. 解析与打标速率

**现状**：全流程 45~90s（OCR 20~40s + 打标 5~20s）；`smart_batch_size` 已对超过 8 页的简历动态调整批次大小；图片分辨率固定 144 DPI；接口无流式响应，调用方感知延迟高。

**优化方向**

| 问题 | 方案 | 预期收益 |
|------|------|---------|
| OCR 耗时 20~40s | 引入 MinerU 本地解析（§1.1），标准简历 2~5s 完成 | 速率提升 5~10x |
| 图片分辨率一刀切 | 单栏纯文字页降至 96 DPI，复杂多栏/表格维持 144 DPI | 渲染 + 传输耗时降低 |
| 打标等待解析完成 | 解析完成 `candidate` 基本信息后立即并发启动打标，不等全量 JSON | 整体流水线缩短 5~15s |
| 重复 PDF 全量处理 | MD5 结果缓存，跳过所有 LLM 调用 | 批量重投场景减少 50%+ |
| 无流式响应 | OpenAI 兼容接口支持 `stream=true`，逐字段推送 | 改善调用方感知延迟 |

## 4. 扩展性（按实际需求取舍）

**中台定位说明**：内存任务缓存（TTL 10min，重启丢失）和 `tag_config_runtime.json` 本地文件是无状态中台的设计选择，符合"调用方自行存储"的定位，不作为核心扩展性问题。

**仍值得关注的扩展方向**：

| 场景 | 当前瓶颈 | 方案 |
|------|---------|------|
| 高并发削峰 | 线程池（`MAX_WORKERS=24`）是唯一背压手段，打满后新任务排队 | 前置 RocketMQ/Kafka 队列，服务按能力消费 |
| 可观测性 | 无 metrics，LLM 调用延迟/失败率不可见 | 接入 Prometheus：暴露 LLM 调用延迟、失败率、任务队列深度 |
| 多节点标签配置同步 | `tag_config_runtime.json` 各节点独立（仅在多实例部署时有影响） | 如需多节点，可将 CRUD 写操作指向中心 Redis Hash 或配置中心 |

---

## 5. 安全与稳定性

- **安全加固**：上传文件仅校验 `%PDF` 魔数，建议补充 MIME 类型验证和文件大小二次限流，防止畸形文件绕过。
- **PDF 预检增强**：现有 `_open_pdf` 已检测加密 PDF；可进一步对扫描件低质量（低分辨率图片页）和超长简历（>30 页）提前拒绝或降级，避免无效 LLM 消耗。
- **LLM 超时保护**：当前 `API_TIMEOUT=300s`，建议对 MinerU 路径设置独立超时（30s），降级回多模态路径时重新计时。

## 优先级建议

| 优先级 | 项目 | 预期收益 |
|:------:|------|---------|
| 🔴 高 | 打标输入压缩（去掉 description） | 单次打标 token 降低 40~60%，速率提升 |
| 🔴 高 | 规则后校验层（phone/email/date 正则） | 关键字段格式准确率显著提升 |
| 🔴 高 | MinerU 接入（PDF→Markdown 本地化） | OCR 速率提升 5~10x，多模态 token 减少 80%+ |
| 🟡 中 | MD5 结果缓存 | 批量重投场景 LLM 调用减少 50%+ |
| 🟡 中 | 开源小多模态模型（InternVL2-8B / Qwen2-VL-7B）替代 397B | 降低大模型资源消耗，提升扫描件覆盖率 |
| 🟡 中 | 模糊合并策略（编辑距离跨批去重） | 长简历解析准确率提升 |
| 🟢 低 | 消息队列接入 | 高并发削峰，架构升级成本较高 |
| 🟢 低 | 流式响应支持 | 改善调用方体验，不影响吞吐 |
