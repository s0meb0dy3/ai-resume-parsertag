# AIHR 简历解析服务 — 优化方向分析

> 版本：v1.1  日期：2026-05-28

---

## 1. 降低多模态大模型依赖（核心目标）

**现状**：
- 阶段一（OCR 解析）：每份简历至少 1 次多模态 LLM 调用，超过 8 页时按 `smart_batch_size` 分批，每批仍独立发起多模态调用；图片统一以 `detail="high"` 144 DPI 渲染，token 消耗高。
- 阶段二（打标）：1 次**纯文本** LLM 调用（非多模态），但 Prompt 注入了完整简历 JSON，含 `works[].description`、`projects[].description` 等大段描述文本，无效 token 占比高。
- 已有规则降级层（`extract_positive_tags_rule`），LLM 打标失败时可自动回退，但平时未充分利用。

**优化方向**

| 问题 | 方案 |
|------|------|
| 多模态 token 消耗高 | 混合提取：姓名、电话、邮件、日期等强结构化字段用 PaddleOCR 或正则预提取，仅将自评、项目描述等非结构化字段交给多模态 LLM，可减少 30~50% 图片 token |
| 打标输入过长 | 压缩打标 Prompt：只传 `works[].company/position`、`educations[].school/degree`、技能关键词，去掉 `description` 长文本，token 消耗可降低约 40% |
| 相同 PDF 重复解析 | 对文件内容做 MD5 哈希，命中缓存直接返回已有结果，彻底跳过两次 LLM 调用；对批量重投场景效果显著 |
| `detail` 固定 high | DPI 自适应：单栏纯文字页降至 96 DPI / `detail="low"`，多栏表格/复杂排版页保持 144 DPI / `detail="high"`，由像素密度自动判断 |
| 规则层利用不足 | 强化现有规则降级路径：学历、工作年限、公司背景等确定性维度优先走规则层，仅 skills、industry 等推断维度调用 LLM，降低无谓调用量 |

## 2. 解析与打标准确性

**现状**：
- 电话、邮件、日期等强结构化字段完全依赖 LLM 提取，容易格式漂移（如电话缺位、日期格式不统一），目前依赖 `json_repair` 兜底。
- 超过 8 页时分批并发，跨批次合并依赖 `company+startDate` 精确匹配去重，公司名称轻微差异（如缩写/全称）会导致同一段工作经历重复或拆分。
- LLM 修复过的字段无可信度标记，调用方无法感知哪些字段存在低置信风险。

**优化方向**

- **规则后校验层**：LLM 输出后用正则对关键字段做格式修正——电话 `1[3-9]\d{9}`、邮件标准格式、`startDate/endDate` 统一为 `\d{4}-\d{2}`，减少 `json_repair` 兜底频率，提升字段一致性。
- **模糊合并策略**：跨批次合并 `works[]` 时改用公司名编辑距离匹配（而非精确匹配），容忍轻微名称差异，避免同一段经历被拆分成多条。
- **置信度标注**：对 `json_repair` 修复过的字段在内部打上 `_repaired` 标记，供调用方识别低可信字段，支撑后续人工审核流程。
- **打标规则层补强**：扩充 `tag_data.py` 中的大厂、院校、行业词典，减少 LLM 对规则可覆盖场景的介入，提升确定性维度的准确率。
- **反馈闭环**：收集调用方标注的解析错误，定期回归测试，监控关键字段准确率趋势。

## 3. 解析与打标速率

**现状**：单份简历全流程 45~90s，OCR 解析 20~40s + 打标 5~20s；`smart_batch_size` 已对超过 8 页的简历动态调整分批大小，但基准分辨率和单页渲染策略仍有优化空间；接口无流式响应，调用方感知延迟高。

**优化方向**

| 问题 | 方案 |
|------|------|
| 相同 PDF 重复处理 | MD5 结果缓存（同 §1），跳过全部 LLM 调用，直接返回缓存结果 |
| 图片分辨率一刀切 | 排版简单的简历降至 96 DPI，复杂多栏/表格布局维持 144 DPI，降低渲染和传输耗时 |
| 打标串行等待 | 解析阶段流式输出 `candidate` 基本信息后立即并发启动打标，无需等待完整 JSON，缩短打标等待时间 |
| 无流式响应 | OpenAI 兼容接口支持 `stream=true`，逐字段推送，减少调用方感知延迟 |
| 空白/图片页也占批次 | 分批前检测空白页和纯图片页，可合并或跳过，减少无效 LLM 调用次数 |

---

## 4. 扩展性

**现状**：任务状态纯内存存储（重启丢失）；`tag_config_runtime.json` 为本地文件，多实例部署时各节点配置不同步；无消息队列，线程池是唯一背压手段；缺乏可观测性指标。

**优化方向**

| 场景 | 当前瓶颈 | 方案 |
|------|---------|------|
| 水平扩展 | 内存任务不共享 | 任务状态迁移到 Redis，key=taskId，支持多实例轮询 |
| 配置多实例同步 | runtime.json 本地文件 | 配置持久化到 Redis Hash 或数据库，CRUD 写中心存储 |
| 高并发削峰 | 线程池是唯一背压 | 前置 RocketMQ/Kafka 队列，服务按能力消费，避免线程池打满 |
| 可观测性 | 无 metrics | 接入 Prometheus：暴露 LLM 调用延迟、失败率、任务队列深度等指标 |
| 失败自动重试 | 调用方手动重提 | 队列侧配置重试策略（最多 3 次，指数退避），死信队列兜底告警 |

---

## 5. 其他优化点

- **结果持久化**：当前仅写 `results/*.json` 本地文件，多实例或容器重启后不可查询；建议写入 MySQL/MongoDB，支持按 taskId 检索历史结果。
- **安全加固**：上传文件仅校验 `%PDF` 魔数，建议补充 MIME 类型二次验证和文件大小限流，防止畸形文件绕过。
- **PDF 预检增强**：现有 `_open_pdf` 已检测加密 PDF；可进一步对扫描件质量（低分辨率图片页）和超长简历（>30 页）提前拒绝或降级处理，避免无效 LLM 消耗。

## 优先级建议

| 优先级 | 项目 | 预期收益 |
|:------:|------|---------|
| 🔴 高 | 打标输入压缩（去掉 description） | 单次打标 token 降低约 40%，速率提升 |
| 🔴 高 | MD5 结果缓存 | 批量重投场景 LLM 调用减少 50%+ |
| 🔴 高 | 规则后校验层（phone/email/date 正则） | 关键字段格式准确率显著提升 |
| 🟡 中 | 混合提取（PaddleOCR 预提取结构化字段） | 多模态 token 减少 30~50%，但引入新依赖 |
| 🟡 中 | 模糊合并策略（编辑距离去重） | 长简历跨批准确率提升 |
| 🟡 中 | Redis 任务状态 | 支持水平扩展 |
| 🟢 低 | 消息队列接入 | 高并发削峰，架构升级成本较高 |
| 🟢 低 | 流式响应支持 | 改善调用方体验，不影响吞吐 |
